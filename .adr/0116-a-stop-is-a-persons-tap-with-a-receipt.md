# 0116: a Stop is a person's tap with a receipt

- **Status:** Accepted
- **Date:** 2026-10-23
- **Shipped in:** 1.24.0
- **Trail:** asked by Altan on 2026-10-23 ("let's also add a stop button, just saw that a lot of mobile harnesses have that") · every surface profile has carried `keys.interrupt` since the profiles began, and nothing pressed it · the Keys board's Esc and `^C` (`web/src/lib/key-board.ts`) go through `POST /api/pane/:id/keys`, which has no request id and no receipt · v2's Control names `abort` · `bridge/surface/stop.ts` (`StopService`) · `web/src/lib/surface/stop.ts` (the receipt's wire shape) · `bridge/server.ts` (`stopRoute`) · `bridge/surface/shadow.ts` (`canStopOf`) · `bridge/surface/key-gate.ts` (`person_tap`) · `web/src/lib/arm.ts` (`ARM_MS`, `ARM_DWELL_MS`) · `web/src/components/harness-bar.tsx` (`ScreenStop`) · `web/src/components/send-notice.tsx` (`stopNotice`) · `web/src/lib/surface/profiles/*.json` (`keys.interrupt`, `keys.interruptClearsDraft`) · `bridge/crew/forward.ts` (`FORWARDABLE`) · `web/e2e/rig/stop.spec.ts` (case 25) · counsel: none yet, the browser leg is the proof · [ADR 0053](./0053-an-unread-dialog-still-has-a-way-out.md) · [ADR 0101](./0101-a-control-on-a-screenless-pane-names-the-turn-it-saw.md)

## Context

A running turn on a pane with a screen could not be stopped from the phone in one clear step. The profile of every harness names its interrupt key. Nothing read it. The Keys board has an Esc button and a one-tap `^C`, but those are raw key presses. They carry no request id, they read no screen first, and they answer no receipt. The phone cannot tell a person whether the turn stopped.

The wrong key is also easy to press. Escape answers a dialog. In some harnesses Ctrl+C clears a draft before it interrupts. A blind press can deny a permission or throw away text.

A program (a durable pane) already has a Stop. Its `abortTurn` capability, its request id and its receipt come from [ADR 0101](./0101-a-control-on-a-screenless-pane-names-the-turn-it-saw.md). v2 names the same control, `abort`. A pane with a screen should get the same button with the same receipt.

## Decision

**A Stop is a person's tap. It carries a request id. It answers a receipt. Collie presses only the key the profile names.**

1. **One route for both kinds of pane.** `POST /api/pane/:id/abort` takes `{ requestId }` and answers `{ requestId, outcome, reason?, keys? }`. For a program it does what it did. For a pane with a screen it reads the Surface, presses `keys.interrupt` through the key gate as `person_tap`, reads the screen again, and answers.
2. **Arm, then tap.** The first tap on the belt button only arms it. The word changes to "Stop?" and the arm ends by itself after `ARM_MS` (4 s, the value the Escape card of ADR 0053 uses; both read `web/src/lib/arm.ts`). The second tap sends one request, and it counts only `ARM_DWELL_MS` (400 ms) or more after the arm: a tap inside that window is the same touch landing twice, and it is ignored, neither a Stop nor a disarm. The arm also ends when the pane changes or the turn leaves running. While the request is in flight, the button takes no tap. There is no long press and no keyboard shortcut. **The button is always drawn, dimmed when idle.** The belt draws Stop at its start for every pane whose profile names a key (`canStop`), whatever the turn does. While the turn does not read running the button is dimmed in place (`aria-disabled="true"`, not the `disabled` attribute, so it stays in the focus order). It keeps its place and its width, so no other button moves under the thumb when a turn starts or ends (DESIGN.md §2). A tap on the dimmed button sends no request and arms nothing. A pane with no profile, or a profile with no interrupt key, draws nothing.
3. **The Surface decides before a key goes.** The bridge reads the screen twice before the key, the second time right before the press, and each read applies the same refusals. A dialog that draws after the first read is refused too, so the only window left is the press itself. The bridge presses nothing when:
   - `no_profile`: Collie has no reader for the pane, or the profile is revoked. It does not stop a pane blind.
   - `turn_idle`: the turn has already ended.
   - `dialog_open`: a dialog is up, and Escape would answer it. The card is the way.
   - `draft_present`: the box holds text and this harness's interrupt key clears it first (`keys.interruptClearsDraft`).
   - `unreadable`: the screen does not say whether a turn runs or a dialog is up.
   - `press_failed`: the multiplexer refused the keys.
   - `pane_gone`: the multiplexer could not read the pane.
4. **The harness's key is profile data.** `keys.interrupt` is a list of keys pressed in one call. A harness that needs two Escapes names `["Escape", "Escape"]`. `keys.interruptClearsDraft: true` marks a key that clears a draft first. No harness name lives in the bridge or the web app. The pane view says `canStop: true` only when the profile names a key and is not revoked, and the phone draws the button from that word alone.
5. **The receipt has three outcomes.** `stopped`: the keys went in and two reads in a row show the turn idle and no dialog. `pressed`: the keys went in and the read-back did not show that, so the phone says "Stop sent. The agent still looks busy." `refused`: no key left, with one reason from the list above. The read-back makes up to three reads, at 0.4 s, 1.4 s and 2.4 s after the press. `stopped` needs two of them in a row (0.4 s and 1.4 s, or 1.4 s and 2.4 s), because one idle read may be a redraw between two tool calls. A single idle read gives `pressed`.
6. **A person's tap only.** Walky talky, a hook, the CLI and a queued action never run a Stop. Only a `person_tap` token may carry Escape through the key gate, and a Stop is one.
7. **The crew forwards it.** `abort` is in the forwardable pane routes. The member that owns the pane runs the press and the read-back and answers the receipt. The lead relays it. A missing pane answers the Stop's own receipt (`pane_gone`) with its 404, so the phone can tell it from a member whose build has no Stop for a screen pane: that member answers a bare 404, or a 400 from the program-only abort route, and the phone says `unsupported_build` ("This machine cannot stop from the phone yet. Update it."). The lead dials the member once on the forwarded-write budget (5 s) and never again. When no answer comes back in time, the phone says `unknown`: the key may have gone in, so the person reads the pane before a second tap. `unsupported_build` and `unknown` are the phone's words; the bridge never answers them.
8. **The same request id answers the same receipt and presses once.** A request id still in flight is joined, never pressed twice. A request id used on another pane is refused 409. The receipts live in memory, 256 of them, oldest dropped first. A request id dropped from the 256, oldest first, can press again on a replay.
9. **A Stop takes no pane lock.** It must not wait behind a send. One audit line records the request id, the pane, the keys by name and the outcome. It never records a message text.

## What this changes in the Send Protocol

The header of `bridge/surface/protocol.ts` said "Escape is never sent". That rule narrows to: **a protocol token never carries Escape; a person's Stop does, through the key gate, with a receipt.** A send, a command, a queue press or a walky talky message still types and presses only what the profile names for them. Escape stays out of all of them. The Stop is not a send. It is its own route, with its own receipt, and a tap starts it.

## Consequences

- A phone can stop a turn on every harness whose profile names an interrupt key, and it is told whether the turn stopped. A Keys board press stays what it was: a raw key, no receipt.
- Collie never answers a dialog by accident with a Stop. It never clears a draft by accident either. The cost is a refusal the person reads and acts on: answer the card, or empty the box, then stop.
- A harness whose key is not Escape (Ctrl+C for Grok, Cursor and Hermes) needs no code. Its profile says so.
- **Known limit: the replay lives in memory.** A bridge restart between two taps with the same request id forgets the first receipt. A request id dropped from the 256-id memory, oldest first, is forgotten the same way. The second tap can then press a second time. A Stop is a tap and not a message, so the harm is a second interrupt of a turn the person meant to stop, and the Surface check refuses it when the turn has ended. The limit is stated here and not hidden.
- **Known limit: a Stop while messages are queued.** What the harness does with its queue after the interrupt key is not captured yet. It may put the queued lines back into the box, or it may start the next turn with them. The receipt reads the screen only: it says `stopped` when the turn reads idle twice, whatever happened to the queue. A next turn that starts at once reads as running, so the receipt says `pressed`.
- **A `stopped` receipt also ends the hook's running block.** Some harnesses fire no stop hook when the interrupt key ends a turn: Claude Code 2.1.309 fires none on Escape and none on a refused permission. The prompt hook's running block then kept `turn` at `running` after the receipt said `stopped`, 11 s in the second live rerun of Edge 5 (2026-10-23), and 20 s and more when Escape came before the first token, because Claude Code puts the prompt back into the box and the screen shows no stopped row. The bridge now gives each `stopped` receipt to the pane's fold as a `stop` edge, counted as `stop-receipt`. Like a hook's stop edge it ends the blocks and makes no free: the turn is the screen's claim again. A replay, a `pressed` receipt and a refusal give nothing.
- **Known limit: Claude Code shows no running sign while it streams plain text.** Captured on 2.1.309 at 120 by 40, in the fullscreen TUI and in the default one (2026-10-23): while a long answer with no tool call streams, the rows above the box hold only the answer. No spinner row, no `esc to interrupt` and no token counter stand there; the spinner shows only while the model thinks or a tool runs. The prompt glyph's colour differs, but it is grey on some idle screens too, so it is no sign. The screen therefore reads the turn idle, and the hook's running block holds `turn` at `running` until the lost-Stop reads end it: three free reads over 10 s. After that the Stop is refused `turn_idle` and a plain send is sent as if the agent were idle, and Claude Code queues it. This fallback is older than Edge 5 (the lost-Stop reads came with M56 spec 11 on 2026-10-16). Edge 5 makes it visible, because the Stop button, which then was drawn only while a turn ran, left with it. The button now stays and is dimmed, so the person sees the same button but cannot tap it on the idle read. The fallback stays: without it a lost Stop hook would hold a finished turn at `running` forever. The limit is stated here and not hidden.
- A `pressed` receipt is honest about doubt. The turn may need a moment longer, or the harness may have taken the key as something else. The person can tap again.
- A program keeps the Stop it had, with the turn id and the ask id of ADR 0101. The two never draw together, because a program pane never carries `canStop`.
- Stopping a background task or a subagent is not part of this decision. Neither is a Stop that then sends a message.

## Clear (2026-10-24)

The Keys board gets a **Clear** button that empties the harness's input box in one tap (asked by Altan on 2026-10-24: "a clear all inputs button when pressing on keys"). It is not a new ADR because it reuses this one's route shape: `POST /api/pane/:id/clear` takes `{ requestId }` and answers `{ requestId, outcome, reason? }` with `cleared` or `refused`, always 200, through the same request id, 256-id replay, `person_tap` key gate, no pane lock, audit line without text, crew forwarding and `unsupported_build` / `unknown` phone words as the Stop. It invents no key. It presses `keys.clear`, the profile's own delete key, `length + slack` times, the step the Send Protocol already uses to replace a draft (`bridge/surface/protocol.ts`, `clear`). `/api/send` with `mode: "replace"` and an empty text was not used, because a send refuses an empty text and its receipt speaks of a message. The bridge reads the Surface twice before the key (`bridge/surface/clear.ts`) and presses nothing when `no_profile`, `no_draft` (the box already reads empty), `dialog_open`, `unreadable` or `pane_gone`. After the press it reads back up to four times, and `cleared` needs the box to read empty with no dialog; else `press_failed`. A draft longer than one 256-key batch takes a further round, but only from a fresh read that shows the box shorter than before the last press, so no press is blind. A box that did not shrink is left alone. The button has no arm, is greyed when the box reads empty, a dialog is up or the link is down, and takes no tap while a request is in flight. The profile check already refuses Escape as a clear key (`keys.clear.key`), so a Clear never answers a dialog by accident either.

**Restore (counsel, 2026-10-24).** A one-tap Clear can lose a long draft, so a `cleared` receipt carries the text the first read showed in the box, `draft`, one line (the box's rows joined with a space), at most 8 KiB. The route sits behind the same write gate as the tap and the text is the operator's own, but the bridge still never logs it and never writes it to the audit line, whose detail is named fields only. Where the bridge masks secret shapes (`redact`) and the text holds one, the receipt goes without it, because a Restore would type the mask. The phone keeps the text in the composer's state for that pane and shows the receipt as a floating notice above the belt, with the held card and the terminal-draft notice (ADR 0061), so it moves neither the composer nor the belt (an in-flow notice did, on Altan's phone the same day). Beside `Box cleared.` stands **Restore**, offered once a read after the Clear shows the box empty and no dialog, until a read shows a draft again, the pane changes, or two minutes pass. Restore types the text back through the keys route (`POST /api/pane/:id/keys`) as this person's taps through the key gate, the way Type mode types, with no Enter: a line break or a tab becomes a space. That route has no request id, so the phone takes the offer away as the tap leaves and gives it back only on a refusal that says nothing was typed; one Clear, at most one Restore. The keys route audits a typed character only as a mask. `/api/send` was not used, because every mode of it submits or answers a draft refusal, and a Restore must not press Enter.
